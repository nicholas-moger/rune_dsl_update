# The upstream resolution oracle (v3.1 C1)

Runs the **released rune-lang 9.83.0** Xtext pipeline over `.rosetta` sources in
its own JVM and dumps how it resolves every cross-reference. That dump is the
ground truth the fork's Layer-1 resolution spec is extracted against and pinned
to: where a sensible-looking rule and this dump disagree, **the dump wins**.

```bash
scripts/xtext-oracle/run-oracle.sh --out <file.tsv> <src.rosetta|dir>...
scripts/xtext-oracle/run-oracle.sh --rebuild ...        # FULL rebuild: recompile + re-copy deps
scripts/xtext-oracle/run-oracle.sh --context <dir> ...  # loaded, not dumped
scripts/xtext-oracle/run-oracle.sh --issues <file.tsv> ... # v3.2 seat 8: every validation issue, every severity, with its anchor
```

⚠️ A normal run builds **only** when `target/classes` or `target/lib` is
missing. If you edit the oracle's Java under `scripts/xtext-oracle/src/`, pass
`--rebuild` — otherwise the run silently executes the previously-compiled
classes, and a change you are testing appears to have had no effect.

## The positive control runs on every dump

Before anything is resolved, the driver loads
`oracle-positive-control.rosetta` — a model whose if-condition is a `string` —
and requires upstream to reject it with ``Expected type `boolean`, but got
`string` ``. If that error does not appear, the run **exits 6 and writes no
dump**.

It is not optional, because the failure it guards against looks exactly like
success. The validation leg once returned **zero issues for every input**: the
build shaded its dependencies into an uber-jar, a shaded jar cannot carry two
files at the same path, nearly every Eclipse/EMF artifact ships a
`plugin.properties`, EMF could not build its diagnostic root, and validation
came back empty — indistinguishable from a language with no complaints. Two
recorded conclusions had to be retracted. Dependencies are now **copied, not
shaded** (see the pom), and the control is what proves that stayed true.

The control gets its **own `XtextResourceSet`**, so its declarations can never
enter a subject's scope — verified by regenerating the committed dump with the
control active and diffing byte-for-byte. `ORACLE_CONTROL` overrides the path;
there is deliberately no flag to skip it.

The committed dump for the conformance suite lives at
`rune-parser/src/test/resources/resolution-conformance/upstream-9.83.0.tsv` and
is regenerated by pointing the driver at that directory. Output is sorted and
byte-stable across runs (verified).

## The oracle law

The **released 9.83.0 jars** are the oracle — never the vendored `rune-dsl/`
source. That tree sits at `10.0.0-dev.8` and its grammar has *removed* syntax
9.83.0 still accepts (`regulatoryReference`, `using standard`, rule `as`
identifiers, `segment` compat names, `label ... as`), so parsing 9.83.0 corpus
sources with it would fail on valid input. Inherited verbatim from
`scripts/holdout-oracle`, which pins byte-goldens under the same rule.

Reading the vendored source is a different matter and is safe **for this
surface**: `git diff 9.83.0 HEAD` inside `rune-dsl/` leaves
`RosettaScopeProvider`, `types/`, `RosettaEcoreUtil` and `utils/`
byte-identical, and the one scoping delta (`ReversedSimpleScope.getElements(EObject)`)
is the serializer's object→name path, not the textual lookup that decides
precedence. So the vendored tree is a faithful **reading** reference and never
the **executing** oracle. Re-check that diff before trusting it for a new
surface.

## Why a separate process

The fork and upstream both own the package `com.regnosys.rosetta.*` with
incompatible shapes — `com.regnosys.rosetta.types.RType` is an *interface* in
the fork and a *class* upstream. Put both on one classpath and Guice dies:

```
IncompatibleClassChangeError: class com.regnosys.rosetta.types.RDataType
                              has interface com.regnosys.rosetta.types.RType as super class
```

In-process differential execution is therefore **structurally impossible**, not
merely unwired. This is why the predecessor `XtextEquivalenceHarness` never
compared anything: its `compareCrossRefs` returned an empty list, and its Xtext
side failed to boot behind a caught exception and a one-line warning, so the
test passed green while measuring nothing. That harness is superseded by this
tool.

There are **two build pins**, both explained in full by the scaffold pom. First,
jar signatures **must** be stripped (seven separately-signed Eclipse jars share
the package
`org.eclipse.core.runtime`) — done per-jar by the committed
`strip-jar-signatures.py`, which reports what it could not fix and exits
non-zero, because its predecessor was `zip -d … || true` with no `zip` on this
box: it stripped nothing and wrote a "done" marker anyway. Second,
`org.eclipse.emf.common` **must** be pinned forward to 2.44.0 (rune-lang 9.83.0
resolves it to 2.30.0 while ecore lands at 2.42.0, and the injector dies on
`CommonUtil.newURL`).

## Output contract

```
XREF <file> <offset> <length> <srcEClass> <EClass.feature> <sourceText> <targetEClass> <targetFqn>
LINKERR <file> <line> <message>
VALIDERR <file> <line> <message>
```

and, with `--issues <file.tsv>`, a SECOND file with its own pinned header
(`# rune-xtext-resolution-oracle 9.83.0 issues=N columns=...`):

```
ISSUE <file> <line> <column> <offset> <length> <severity> <message>
```

`line` and `column` are 1-based; `offset` is a 0-based CHARACTER index and
`length` a character count — Xtext's units (the fork's `SourceRange` offsets
are UTF-8 BYTES; the two coincide on ASCII input, so a cross-tool comparison
reads line and column). Every severity is recorded, sorted by file, line,
column and offset as numbers. This is how a fork diagnostic ANCHOR is measured
against the released validator's on an invalid fixture (v3.2 seat 8 round 2:
the only-exists anchors — the dump's own contract above is untouched).

`offset` is the cross-reference's **own** node, so each link in `a -> b -> c`
gets a distinct key and the fork's dump pairs against this one positionally.
Offsets are zero-padded so the plain text sort is also a positional sort.

`LINKERR` records are part of the contract, not noise: upstream *refusing* to
bind a name is a fact the fork must reproduce. The conformance suite relies on
this — `C1OutputInConditions` names the function output from a pre-condition,
upstream filters the output out of that scope, and the expected answer is
`UNRESOLVED`. A resolver that binds it is wrong.

`VALIDERR` records are the VALIDATION leg — issues at `ERROR` severity from
upstream's validator, which is a separate pass from linking and was not being
invoked at all until the C1 instrument audit found it. They are in the contract
for the same reason as `LINKERR`: "upstream rejects this" is a fact the fork
must reproduce, and the error-count differential is built on them. Warnings are
printed to stderr but are NOT recorded in the dump; `--issues` records every
severity, warnings included, to its own file (v3.2 seat 8).

The header line carries a record count so an empty dump is distinguishable from
a dump whose oracle silently failed to boot — the exact failure mode of the
harness this replaces. The driver treats any non-zero exit as fatal and tells
you not to commit the result, and the wrapper additionally refuses a dump whose
pinned header is missing, so a run that exits 0 without writing cannot pass as a
success either.

## Requirements

* `org.finos.rune:rune-lang:9.83.0` and its dependencies in `~/.m2` (the box
  gates offline).
* The builtin models, defaulted to
  `test-corpus/rune-dsl-builtins/rune-runtime/src/main/resources/model`
  (`ORACLE_BUILTINS` overrides). Without them `string`, `boolean` and every
  annotation resolve to nothing and the dump is meaningless.
* A model that uses meta features must declare its own `metaType` root elements
  (as cdm's `base-desc.rosetta` does) — upstream resolves them through
  `RosettaConfigExtension.findMetaTypes` against exported `metaType`
  declarations, **not** against the `metadata` annotation's attributes.

The compiled classes and the ~40 MB of copied dependencies are built on demand
into `target/` and are gitignored. Only the TSV dumps, the control model and
the sources are committed.
