# Hold-out oracle — pinning byte-goldens from the released 9.83.0 plugin

**W42 sweep leg B slice 2 (PR #410).** Pins per-group byte-goldens for the hold-out
corpus (`rune-java-generator/src/test/resources/holdout/`) by running the **released**
`com.regnosys.rosetta:rosetta-maven-plugin:9.83.0` from `~/.m2` over each group's
fixture models. The goldens land at
`rune-java-generator/src/test/resources/holdout-goldens/<group>/` and are the
comparison target of `HoldOutByteCompareTest` (the leg-B fourth bar).

## The oracle law

The oracle is the **released 9.83.0 plugin JAR chain** — NEVER the vendored
`rune-dsl/` source tree, which is `0.0.0.main-SNAPSHOT` (post-9.83); building it as
the oracle would silently corrupt the comparison. `pom-template.xml`'s header
records the full configuration provenance (mirrored from the CDM 6.20.6
`rosetta-source` pom, the canonical 9.83.0-era consumer) and the three deliberate
deltas (raw un-filtered sourceRoots; the omitted `classPathLookupFilter`; no
`rosettaConfig`).

## Usage (from the repo root)

```bash
scripts/holdout-oracle/run-holdout-oracle.sh              # all groups
scripts/holdout-oracle/run-holdout-oracle.sh pojo         # one group
```

Per group the driver: stages the fixtures RAW into a fresh scaffold under
`target/holdout-oracle/work/<group>/`, runs the plugin TWICE from scratch,
byte-compares the two runs (a nondeterministic oracle cannot pin goldens — any
diff fails the group), then installs run 1 as the group's goldens
(delete-then-copy; the goldens dir is single-owner, this script).

A group MAY carry a `rosetta-config.yml` (PR #422): the driver stages it at
the scaffold root (outside the model dir) and passes it to the mojo via
`<rosettaConfig>` with an absolute native path. This is the opt-in for
upstream's experimental-feature gating — `func-extends-valid` enables
`scopes`, which `func ... extends` requires ("You can only extend a function
in a file with a scope"; scopes themselves are gated: "Scopes are an
experimental feature, and are not enabled for this project"). Opt-in configs
keep the default model name and no generators section, so generated bytes are
config-neutral; only validation gating changes. The fork-side loader ignores
the file (it enumerates `*.rosetta` only). Zero-emission
groups (alias-only models) install an EMPTY goldens dir — git does not track
empty directories, so `HoldOutByteCompareTest` treats an absent group dir as the
empty golden set. The no-args sweep skips the two oracle-rejected groups (§
population notes) so it exits 0; name one explicitly to reproduce the refusal.

Note: the scaffold runs inside the repo tree, so Maven picks up the repo-root
`.mvn` (the build-cache extension). Harmless by construction — `generate-sources`
builds never SAVE to the cache ("no artifacts to save"), so run 2 can never be a
cache restore and the determinism gate keeps its teeth (Seat-1 #410 OBS-4).

## Population notes (2026-07-16 run)

- 7 of 9 groups pin goldens: 210 files total, all deterministic ×2.
- `formatting-nestedConstructor` + `formatting-onlyExists` are formatter-INPUT
  fixtures with deliberately unresolvable references: the oracle REFUSES them
  ("severe validation error" — the mojo's validation gate), so no golden is
  definable. They stay covered by slice 1's golden-free bars
  (`HoldOutGenerationTest`).
- Version law: models without a `version` declaration emit `@version 0.0.0`
  (upstream's EMF default, `RosettaModelImpl.VERSION_EDEFAULT`); declared
  versions (hero-model's `"test"`) pass through. The fork side mirrors this with
  the loader stamp in `HoldOutByteCompareTest`.

Re-run ONLY to re-pin deliberately (a generation-behaviour change on the oracle
side can only come from a plugin-version bump — which would be a corpus/version
rebaseline event, not a routine regen).
