# Byte-diff catalogue

This directory holds the rune-dsl-plus Layer-4 parity gate — a classified ledger of every remaining byte-level divergence between our generated output and the upstream rune-dsl baseline, after Layer-3 normalisation.

> **Authoritative skill:** `byte-diff-catalogue.md` (local, in the maintainer skill store).
> **Authoritative D-entries:** D5 (local) (schema + storage), D17 (local) (japicmp baseline), D19 (local) (proposer-only auto-gen + §4.3 stylistic acceptance) — all in the development decision log.

## Layout

```
docs/byte-diff-catalogue/
├── schema.json                            # JSON Schema Draft 2020-12 (authoritative)
├── README.md                              # this file
├── index.json                             # generator-emitted; do NOT hand-edit
└── <corpus>/<version>/<entry_id>.json     # one file per entry
```

`index.json` is regenerated by `scripts/byte-diff/generate_index.py` and is enforced by CI's `index-regen-check` job. Hand-edits to it are reverted on next regeneration.

## Adding an entry

1. Generate a UUIDv4: `python3 -c "import uuid; print(uuid.uuid4())"`.
2. Create `docs/byte-diff-catalogue/<corpus>/<version>/<uuid>.json` with the 14 D5 (local) fields. Filename stem MUST equal `entry_id`.
3. Run `bash scripts/byte-diff/validate.sh` — must exit 0.
4. Run `python3 scripts/byte-diff/generate_index.py` — refreshes `index.json`.
5. Commit BOTH the new entry file AND the refreshed `index.json` in the same commit.
6. Open PR; CI re-runs validator + index-regen-check.

## Class-rule entries

A "class-rule" entry catalogues an equivalence class (e.g., §4.3 `StringBuilder` ↔ `StringConcatFactory`) rather than a single symbol's divergence. Convention:

- `symbol` uses the reserved prefix `__class_rule__:<slug>` (e.g., `__class_rule__:stringbuilder_stringconcat_equivalence`).
- `upstream_hash` and `our_hash` are both the SHA-256 sentinel for the empty byte string: `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855`. The sentinel is grep-friendly ("show me all class-rule entries").
- The `__class_rule__:` prefix is the discriminator. Future Layer-3 lookup MUST key on `symbol` (not solely on hash pair) so that no real divergence is ever masked by the sentinel.

## Promoting a japicmp proposed entry

The CI job `japicmp-propose` uploads a workflow artefact `byte-diff-proposals-<run_id>` containing `_proposed/japicmp-<sha>.json` — a list of *candidate* entries the heuristic classifier suggested.

D19 (local) part 1 forbids automated promotion. To turn a candidate into a real entry:

1. Download the artefact from the GitHub Actions UI.
2. Pick a candidate from `candidates[]`.
3. Hand-author a real entry per the "Adding an entry" steps above. Use the candidate's `rationale_template` as a starting point, but write a human-meaningful rationale and pick the correct `status` (`accepted` if D-entry-backed; `active` otherwise).
4. The promotion commit carries your git identity — that's the §7.1 audit trail.

## Anti-pattern reference

The skill's §9.1-§9.7 enumerate the anti-patterns this catalogue must guard against. P1.3.3 ships only the static guards (schema validation, index regen check). Runtime guards (stale-triage, reclassification-drift, orphaned-entry) ship later — they depend on Layer-3 matrix-runner and the heuristic classifier source code, neither of which exist yet.
