# Source and validation record

This is the retained detailed record for the 22 September 2026 code snapshot. Start with the [current guide](SOURCE-SNAPSHOT.md) for its present interpretation and scope. The commands and measurements below retain their original validation dates; they are not new runs.

This is the package record of review drop 1 ([Changelog](../CHANGELOG.md)). It identifies the source revision, the packaging differences, the environment, and every check that was executed on the assembled export with its result; it names what was not executed. The review repository's own commit identity is recorded outside this file, because a file cannot carry its own commit hash.

The snapshot was prepared in three steps, each reviewed independently before the next: the initial snapshot; the first correction, after the review of that snapshot (the committed-snapshot review, findings R1-R10); and the second correction, after the review of the first correction (the correction review, findings C1-C3). Each of those reviews had spec, quality and privacy parts, and the initial snapshot and each correction were also checked by two internal review seats (spec and quality) before they were handed back. The steps were separate preparation commits; the first correction is the "correction commit" of the evidence inventory's file descriptions. A final wording pass on this record and the changelog, checked by the same two internal seats and reviewed independently before the single commit was made, prepared them for a single-commit history. The repository carries only the final result, as its single initial commit, so the preparation commits and their hashes are not part of its history. This record keeps what each step changed and what was run on it: rows labelled with a correction were run for it (row 9a records the committed-snapshot review's own run, added to this record by the first correction); the other rows ran on the initial snapshot.

## Findings during validation

1. **Corpus manifest defects (fixed in the manifest, not in the comparison).** The first manifest listed 90 "source" rows that were 87 main sources plus the three CDM test models outside the declared source root, and its 87 source hashes were of a CRLF checkout rather than the pinned Git blobs; against the instructed `core.autocrlf=false` clone every source read as different. The rebuilt manifest is described under § Packaging differences.
2. **Enumeration-order dependence of the released generator.** The order of namespace descriptions in a package-info and of the qualifier registrations in `BusinessEventMeta.java` depends on the generating machine's file enumeration: the builder's regeneration differed from the retained reference in two package-info files, and the committed-snapshot review's regeneration differed in those two and in `BusinessEventMeta.java` (equal registrations and multiplicities, two source-file blocks swapped). Documented with the witnessed forms in [Corpus](CORPUS-9.83.md#files-that-depend-on-the-generating-machines-enumeration-order); no test, pin or register was changed.
3. **Shell lints under WSL.** Invoking `bash` from PowerShell reached WSL over a CRLF checkout and failed on `\r`; under Git Bash the same scripts pass. Documented in [Testing](TESTING.md#integrity-checks).
4. **Suite prerequisites.** The module suites need the public builtin clone and worktree, and the corpus guards fail by design without the full catalogue. Documented in [Testing](TESTING.md#core-suites-in-a-partial-corpus).
5. **japicmp report scope (found in the second correction's run, not changed).** In `rune-japicmp/pom.xml` the `<includes>`, `<excludes>` and `<htmlTitle>` elements of both executions sit directly under `<configuration>` instead of inside `<parameter>`; Maven reports them as unknown and japicmp ignores them, so the report-only Layer 1 report has no package filter: its 1,213 class rows are the 723 public classes present only in the upstream baseline and all 490 public classes of the parser jar (486 new, 4 modified), not only `com.regnosys.rosetta.ast.model`. The access modifier (`public`) and the break-build flags are inside `<parameter>` and apply; the access modifier leaves out the parser jar's other 11 class files, non-public nested classes. The scope statements of the module guide and of [the backward-compatibility guide](bc-verification.md) describe the intended filter; that guide's Layer 3.1 and 3.2 sections and the module guide's ignore-list rule point to this finding; correcting the configuration would change the gate's output and is left to the maintainers.
