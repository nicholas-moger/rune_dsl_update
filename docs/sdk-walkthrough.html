Story 1 · Maintaining the Java target

Same name. Different types.

Based on real upstream issue #1395, using the regression example from its fix, PR #1396.

Original issue #1395 ↗Fix PR #1396 ↗
The real maintenance problem

Two distinct Rune types become the same Java check.

A switch contains two types named CommodityOption, each in a different namespace. The generated Java checks the short name twice, so it cannot distinguish the branches.

What the Rune model means

ns1.CommodityOption → aReturn 1
ns2.CommodityOption → bReturn 2

The namespaces identify different types. Both extend common.Product in the regression example.

What the Java defect does

if (value instanceof CommodityOption) …
else if (value instanceof CommodityOption) …

Illustration of the reported defect: both conditions test the same Java type. PR #1396 reports the second regression case returning the default, −1.

The maintainer’s task: reproduce the wrong result, find where type identity is lost, correct Java generation and prove that both branches work.

This issue is already fixed upstream. We use it as a real maintenance example for designing the replacement developer experience.
